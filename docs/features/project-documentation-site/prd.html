Product requirements Approved
Product requirements · Approved · Updated 2026-07-25

Make every product document feel like one connected system

A self-contained Protocol-styled HTML file makes each PRD and design navigable, expressive, and portable—without a documentation server.

  1. Moment. A maintainer, reviewer, or agent opens a PRD or design to understand a feature without starting another application.
  2. Friction. The current files are durable and portable, but inconsistent presentation makes related product and architecture evidence feel disconnected.
  3. Bet. Generate each PRD and design as one self-contained Protocol-styled HTML document with responsive navigation, diagrams, and restrained semantic scroll motion.
  4. Proof. A reader can open the file directly, navigate its sections, understand an animated causal diagram, disable scripts or motion, and print the complete document.
  5. Boundary. Documentation remains versioned HTML evidence—not a Next.js site, hosted portal, editor, approval engine, or second source of truth.

Protocol presentation without an application runtime

The recognizable sidebar, typography, emerald accents, and mobile navigation live inside each document. Opening the file is the entire deployment model.

Approved direction

Use the licensed Protocol application as visual authority, not as a server dependency. Progressive navigation and motion may enhance reading, but never own content.

Reader path

The document works from direct open through deep review

  1. Open. The reader opens prd.html or design.html directly from the repository or review tool.
  2. Orient. The first viewport identifies artifact type, status, updated date, outcome, and product authority.
  3. Navigate. A desktop section rail or native mobile disclosure is derived from stable authored heading IDs.
  4. Understand. Text explains the complete claim while diagrams reveal causal stages as they enter the viewport.
  5. Review anywhere. Reduced motion, scripts removed, narrow screens, offline reading, and print all preserve the same evidence.
Product contract

Portability and clarity outrank application behavior

  • Every generated artifact is one self-contained HTML file with no required network asset, framework, or server.
  • The PRD or design body remains the source of truth; the shell cannot invent sections or product behavior.
  • Navigation is derived progressively from existing h2[id] headings and is optional to comprehension.
  • Motion is used only for section entry, causal flow, state, or target emphasis and honors reduced-motion preferences.
  • Every diagram has a title, description, caption, text walkthrough, static source order, and readable print result.
  • Stable data-review-id anchors survive regeneration.
Observable proof

One file survives every important reading mode

  • The document renders correctly from a local file:// URL without a build or server.
  • The Protocol shell has a fixed desktop rail, compact top bar, native mobile navigation, and no page-level overflow at 320px.
  • Sections and diagram stages visibly progress as their own content reaches the viewport.
  • Reduced motion and interrupted animation immediately settle all content into a readable state.
  • Removing every script leaves the complete article and diagram visible in source order.
  • Print removes navigation chrome and preserves complete text, figures, captions, and provenance.
Boundary

This improves documents, not documentation infrastructure

In this direction

  • Standalone PRD and design templates.
  • Protocol-derived responsive presentation.
  • Progressive section navigation.
  • Accessible diagrams and semantic scroll motion.
  • Offline, no-JS, reduced-motion, and print completeness.

Not in this direction

  • Next.js or another documentation server.
  • A generated site, feature catalog, database, or search service.
  • Authentication, comments, approval workflows, or browser editing.
  • A duplicate MDX or JSON content authority.
