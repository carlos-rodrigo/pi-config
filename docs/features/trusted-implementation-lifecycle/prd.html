Trusted Implementation Lifecycle

Direct Pi implementation work automatically enters an isolated, verifier-led lifecycle without requiring the user to remember a command, skill, or workflow mode.

Review first

Confirm that only an idle direct human implementation request authorizes one controlled run; every model-reachable mutation route is fail-closed; verification and review bind one immutable evidence tuple; repair is discriminating and bounded; and version one performs no integration.

Explicit human approval

Approved by Product owner on 2026-09-01.

Product

Implementation automatically becomes a controlled delivery run

For a developer delegating implementation in Pi, an idle direct human implementation request automatically starts a quality-gated run, resulting in independently verified merge-ready evidence or a precise safe blocker; unauthorized mutation is blocked without creating authority and ordinary exploration remains unchanged.

Approval brief

Product
Trusted Implementation Lifecycle
Why
The current implementation agent can write, test, review, and declare its own completion, so a polished response can overstate correctness or maintainability.
How it works
Recognize implementation before mutation, enforce a mutation barrier, delegate one isolated writer, run controller-owned verification, obtain independent read-only review, repair at most twice, and return evidence to the human.
Approve
Make this lifecycle automatic for implementation work, preserve explicit human authority, and use risk-tiered independent review without requiring a command, skill invocation, or standing agent team.
Not building
Automatic merge, push, deployment, unbounded repair, mutable parallel workers, automatic policy rewriting, or a generic quality score.
Actor
Developer delegating a code behavior change through normal Pi conversation
Entry
A direct, idle interactive TUI user request that explicitly authorizes one mutation; RPC, extension-generated, queued, steering, follow-up, skill/template-expanded, and model-authored content cannot start a run
Result
MERGE READY, DECISION REQUIRED, or FAILED SAFELY with candidate-bound evidence
Boundary
The controller may coordinate implementation and repair but never grants itself product authority or integrates the result
Problem

Advisory discipline cannot make self-certification trustworthy

Skills improve behavior, but the acting model can still skip them, weaken checks, review its own work, or treat process completion as software completion.

  • Sourced fact — the current implement-task workflow asks the implementation agent to run and resolve its own Are You Proud review.
  • Sourced fact — the current verify extension skips automatic verification in headless sessions.
  • Sourced fact — agent-jobs records process completion, not independently accepted code quality.
  • Sourced fact — worktrees isolate Git state but do not constrain host credentials, filesystem access, or network access.
Consequence

Without controller-owned evidence and separation of duties, a delegated run can report success even when tests are weak, checks were skipped, scope expanded, or the implementation is unnecessarily complex.

Behavior

The controller activates automatically and owns completion

Conversation remains lightweight until implementation is requested; once authorized, mutation, evidence, review, repair, and integration state belong to the controller rather than the writer.

  1. Recognize implementation authority
    Only a direct idle interactive TUI user request with explicit mutation language arms one lifecycle. Extension-generated, queued, steering, follow-up, skill-expanded, prompt-template, and model-authored content cannot create implementation authority; an ambiguous request remains read-only and asks for clarification.
  2. Delegate one isolated writer
    The controller freezes the authorized direct-user request, complete nonignored base snapshot, verification policy, and current base identity; it prepares one detached candidate without copying project environment files and gives exactly one writer role mutation capability. The writer still runs with the user’s local Pi/provider and host permissions until a separate sandbox is approved.
  3. Verify independently
    The controller freezes repository-owned verification before mutation, rejects unauthorized changes to that policy or its tests, runs it against one complete candidate snapshot, and confirms model-reachable checks did not change that snapshot. Missing, failed, stale, or policy-weakened evidence cannot become success.
  4. Review independently
    A fresh process with no writer history or mutable tools receives the frozen authority, base/candidate snapshots, verification-policy digest, tests, commands, and verifier receipt, then returns structured findings and a Proud or needs-attention verdict bound to that immutable review input.
  5. Repair within a bound
    A concrete in-authority verifier failure or Must/Should review finding requires one fresh writer repair unless the same signature repeated, the repair would cross protected authority, or two repairs already ran. One cycle is one repair process followed by a new complete candidate snapshot and both gates; every mutation invalidates earlier receipts.
  6. Return control to the human
    The run terminates as MERGE READY only when the frozen base is unchanged and matching final receipts pass; DECISION REQUIRED for ambiguity, protected scope, or external drift; and FAILED SAFELY for unavailable infrastructure, repeated failure, or exhausted repair. Version one categorically ends before any branch/ref integration commit, merge, push, deployment, or any primary-worktree mutation.
  • Read-only exploration remains available. Model-reachable tests, builds, generators, and unknown shell/custom tools are treated as potentially mutating and run only inside a controlled candidate; direct human shell input remains outside this agent-tool policy.
  • Every model-reachable filesystem or repository mutation—including documentation—is controlled in version one. A direct human request to edit documentation authorizes the same lifecycle; this avoids treating executable instructions or generated policy as harmless prose.
  • A skill may guide a role but cannot create authority, activate, verify, approve, or complete the lifecycle.
  • Every model-reachable tool is denied in the primary session except the controller-owned, final-argument-validating read wrappers; edit, write, bash, PowerShell, unknown extension effects, and parallel sibling calls cannot bypass admission. Direct operational slash commands and direct human shell remain governed by their own explicit human contracts, while final base drift still blocks favorable delivery.
  • One durable lease exists per canonical Git root. Steering, queued/follow-up input and RPC cannot start or alter it. A direct interactive Cancel request sends TERM then KILL to the recorded process group and becomes terminal only after parent-observed process-group exit evidence; session switch/new/resume/fork is refused until terminal, and reload reconciles the recorded lease/process into a non-favorable terminal without permitting stale completion.
  • Verifier and reviewer capabilities are read-only; only one writer/repair process may mutate the candidate. The reviewer uses a controller-owned system prompt/rubric and resource profile with context files, skills, prompts, project extensions, and writer history disabled; candidate instructions are evidence only, and its complete profile plus supplied input is receipt-bound.
  • Run records persist outside the conversation and bind trusted interactive request ID, authority digest, base snapshot, complete candidate snapshot, protected verification-policy closure, commands/results, controller-owned reviewer-profile digest, supplied-review-input digest, repairCount, child process evidence, and terminal state.
  • The initial release authorizes new runs only from interactive TUI input in trusted local repositories. RPC, print, and JSON mutation requests fail closed, and worktree/tool restrictions are not represented as an OS sandbox or secret-isolation boundary.
Product behavior

Implementation intent crosses a deterministic quality boundary

The figure shows the automatic trigger, isolated candidate, independent evidence gates, bounded recovery, and human-owned integration outcome.

  1. An idle direct interactive TUI user message explicitly authorizes one mutation; RPC and the mutation barrier cannot create authority from automated content or an agent’s attempted edit.
  2. The controller freezes authority and creates one isolated candidate for the only mutable writer.
  3. Controller-owned verification and independent review bind the same authority, base, complete candidate, verification-policy, command-result, and review-input tuple, so weakened or stale evidence cannot pass.
  4. Concrete failures may return to the writer twice; ambiguity, protected scope, or exhausted repair stops safely.
  5. Only a passing candidate becomes merge-ready, and the human retains integration authority.

  • AC-002Throughout every primary turn, only controller-owned read wrappers are active. Each wrapper revalidates final invocation arguments, path confinement, and abort state immediately before I/O; changed, unknown, overridden, write-capable, shell, PowerShell, custom-effect, generated-test/build, and mixed parallel sibling calls are blocked and abort without creating authority. Exactly one path-confined no-shell writer may mutate one no-copy-local candidate; reviewer/verifier cannot mutate it, direct human shell remains outside this model-tool policy, and the product makes no OS sandbox or secret-isolation claim.
  • AC-003MERGE READY requires one immutable tuple of trusted interactive authority digest, unchanged base snapshot, complete candidate snapshot, protected verification closure, successful command result, controller-owned effective reviewer profile, complete supplied-review-input digest, bounded review output receipt, and parent-observed child exit evidence. Verification protects the base verify script, repository scripts, package/CI/test configuration, and existing tests from candidate change, runs all frozen commands in a standalone exported snapshot with an isolated credential-free home, and rejects filesystem side effects. A fresh reviewer inherits no conversation or project resources—only the controller prompt and immutable review packet—and must return Proud with no Must/Should finding; all identities are rechecked immediately before finalization.
  • AC-004A repair occurs exactly when a new candidate-attributable in-authority failure has unchanged policy/environment, requires no protected crossing, and repairCount is below two: either a nonzero frozen command or a validated Must/Should finding. The sole run store atomically records the failure signature, invalidates receipts, and increments repairCount before exactly one fresh writer launch; infrastructure, malformed, repeated, protected, or exhausted failures do not consume another attempt. Controller and role capabilities contain no commit, merge, push, remote mutation, or deploy operation; verification has no shared Git metadata or host credential environment, and finalization rechecks primary files, HEAD/tree identity, candidate identity, and zero controller-owned integration. Trusted repository verification still runs as the host user with network access, so untrusted or unattended execution requires stronger containment.

Scope

Trustworthy sequential delivery before mutable parallelism

The first release makes one implementation candidate trustworthy; agent count and autonomous integration are deliberately not goals.

In scope
Automatic implementation activation, write barrier, one isolated writer, explicit verification, independent review, two repairs, durable receipts, and human integration
Non-goals
Parallel mutable workers, autonomous delete/rename operations, auto-merge, branch/ref commit, push, or deploy, hidden policy changes, generic quality scoring, and importing untrusted project extensions
Assumption
The initial adapter authorizes only interactive TUI requests in trusted local Git repositories with a protectable repository-owned verification closure; RPC/print/JSON, untrusted unattended work, or absent credible verification cannot become merge-ready
Mockups
Not applicable — the feature uses existing Pi conversation, status, and follow-up surfaces rather than adding a new interface
Isolation boundary

A Git worktree and tool policy protect repository state but are not an operating-system sandbox. The writer still uses the user’s Pi provider credentials and host permissions. Untrusted or unattended execution remains out of scope until a container or micro-VM routes every model-reachable tool and project command without exposing host secrets.
